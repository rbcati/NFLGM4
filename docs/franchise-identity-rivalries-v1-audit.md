## Authoritative game history

The authoritative detailed game persistence is the per-league IndexedDB `games` store in `src/db/index.js`. Completed-season archival calls `Games.bySeason(seasonId)` and builds a compact `leagueHistory` row with `buildSeasonArchiveSummary()` in `src/core/league-memory.js`.

The UI view state intentionally does not load the full IndexedDB game archive. The canonical presentation inputs already shipped to the UI are therefore:

1. Current season: `league.schedule.weeks[].games[]`.
2. Completed seasons: `league.leagueHistory[].gameIndex[]`, which is produced directly from the persisted season games at rollover.
3. Archived playoff classification: `league.leagueHistory[].playoffBracketSnapshot.rounds[].games[]`, joined to `gameIndex` by canonical game ID.

`src/core/archive/gameArchive.ts` is a best-effort local Game Book cache used by recent-game presentation. It is not the complete multi-season head-to-head authority and is not scanned by the new model.

The helper combines the current schedule and compact completed-season indexes once, then deduplicates by canonical game ID. It does not scan news, logs, standings, record books, or narrative text.

## Exact identities and eligibility

Canonical game IDs are generated by `buildCanonicalGameId()` as:

```text
${seasonId}_w${week}_${homeId}_${awayId}
```

Live fields differ by source:

- Current schedule: `id` / `gameId`, `seasonId`, containing week `week`, numeric `home` and `away`, `played`, and final `homeScore` / `awayScore` after completion.
- Completed-season `gameIndex`: `id`, `week`, `homeId`, `awayId`, `homeScore`, and `awayScore`; the containing season supplies `year` / `seasonId`.
- Playoff snapshot: round `label`, and compact games with `id` / `gameId`, `week`, `homeId`, `awayId`, scores, and winner identity.
- Canonical team identity: `league.teams[].id`; current alignment is `league.teams[].conf` plus `league.teams[].div`.

A meeting is eligible only when:

- both team references normalize to the two supplied canonical team IDs;
- both scores pass the existing strict final-score parser;
- the row is not explicitly unplayed, scheduled, pending, postponed, canceled, or cancelled;
- the game has an existing or derivable canonical game ID; and
- it is not explicitly marked preseason.

Missing scores are never coerced to zero. Future schedule rows serialized as unplayed 0-0 are rejected by the existing strict final-score contract. Ties are retained as factual completed meetings.

The live game does not ship a separate exhibition schedule: the `preseason` phase precedes the official 18-week schedule. Explicit preseason game markers are excluded. Older compact `gameIndex` rows do not preserve a phase field, so unmarked rows receive the same official-season treatment as the existing League/Team History screens; V1 does not guess a missing stage.

## Current and archived seasons

`buildMatchupHistoryContext()` reads the current schedule and the in-view `leagueHistory` rows. `buildViewState()` currently exposes the latest 60 `leagueHistory` summaries, while the IndexedDB Seasons store can retain more. Accordingly, UI wording is always **recorded franchise history**, never **all-time**. V1 does not add a worker request, persistence cache, or schema solely to extend that window.

Older `history.seasons` rows are accepted as a compatibility input when they contain the same compact `gameIndex` shape. Duplicate references from the two containers are removed by canonical game ID.

## Playoff authority

Current playoff games are authoritative when the game or containing week has an explicit playoff flag/round. Archived playoff games are authoritative only when their canonical game ID appears in `playoffBracketSnapshot`.

The live round mapping is reused:

- Wild Card
- Divisional
- Conference Championship
- Championship

A game explicitly marked as postseason but lacking a supported round can still count as a recorded playoff meeting, while its round label remains absent. A late regular-season week is never converted into a playoff game by week number alone. If playoff identity is not authoritative, playoff context is omitted.

## Division and existing rivalry authority

`isDivisionMatchup` is `true` only when both current team records have the same non-null `conf` and `div`; it is `false` for a known different alignment and `null` when alignment is missing.

The repository has no pure canonical completed-game head-to-head aggregator. It does have older rivalry mechanisms: `team.rivalTeamId` is assigned during league creation to one circularly selected same-division neighbor; `updateRivalries()` in `src/core/simulation/scoreKeeper.js` mutates `team.rivalries` scores/events from game traits; `game-runner.js` reads those scores for stakes; and trade/news presentation has separate conference/division “rival” rules. Those mechanisms are not a complete game ledger, and their derived scores are explicitly outside this V1's factual-history guardrails. The new model intentionally consumes none of them. V1 says **Division matchup**, not **rival**, and current alignment does not claim the teams were always in the same division.

## Matchup presentation model

The pure deterministic output is:

```js
{
  teamAId,
  teamBId,
  isDivisionMatchup,
  totalMeetings,
  recentMeetings,
  recentSeries,
  currentSeriesStreak,
  lastMeeting,
  playoffHistory,
  isRematchThisSeason,
  previousCurrentSeasonMeeting,
  availableData,
  omittedReasons,
}
```

Each recent meeting preserves factual `gameId`, season identity, `week`, supported `stage`, home/away team IDs, final scores, winner team ID (or `null` for a tie), and margin.

- Recent series: at most five newest recorded meetings; the sample size is explicit, wins are team-relative, and ties are counted. It is never labeled all-time or complete franchise history.
- Ordering: newest season, then newest week, then supported stage order, then a stable game-ID tie-breaker. Input array order is irrelevant.
- Head-to-head streak: consecutive wins from the newest meeting backward, exposed only at two or more. A tie ends the streak.
- Last meeting: the first item in the deterministic recent ordering, with canonical `gameId` retained.
- Rematch: `true` only when an earlier completed meeting exists in the supplied current season and has a week lower than the upcoming game/current week. A prior-season meeting is not a same-season rematch.

## UI and navigation

The only V1 product integration is the Franchise HQ next-matchup surface. It shows a compact stacked context block immediately below the existing next-game row:

- Division matchup (when current alignment proves it)
- Second meeting this season (when recorded)
- recorded playoff-meeting count (when recorded)
- bounded recent-series line
- qualifying head-to-head streak
- last-meeting score
- safe no-history copy when no prior final is available

The block uses wrapping chips and stacked lines, has no table or nested scroll area, and switches the action below the score at widths up to 430px. The action target is at least 44px high on small screens.

`Open Last Meeting` reuses `buildGameBookDestination(gameId)`, producing the existing `Game Book:<gameId>` destination. The action is exposed only after an existing supported resolver source proves the final is available: a completed current-schedule row, `league.gameById`, the existing synchronous postgame archive, or a successful lookup through the existing `actions.getBoxScore(gameId)` path. A compact `leagueHistory[].gameIndex[]` score alone is not resolver evidence; its factual score remains visible while the action stays hidden. `LeagueDashboard` still owns navigation and the existing Game Detail / Game Book resolver remains unchanged. No new modal, route family, persistence path, or duplicate box-score implementation was added.

Existing history destinations remain unchanged: `History`, `Team History`, `Schedule`, and `Standings`. V1 does not add a second opponent-history block to those screens.

## Performance and legacy behavior

The model is memoized once in Franchise HQ for the single upcoming opponent. It scans the current schedule and compact archived indexes once, filters once for the supplied team pair, sorts once, and returns at most five recent meetings. The model itself performs no persistence reads or worker calls. Franchise HQ performs at most one cached lookup through the existing Game Book action for the single last meeting, and only when the schedule, `gameById`, and synchronous postgame archive cannot already prove resolution. This is an eligibility check, not a new archive loader or per-opponent fan-out.

Legacy/partial data degrades by omission:

- absent archive: current completed schedule only;
- missing alignment: no division label;
- missing scores or incomplete status: no meeting;
- missing playoff authority: no playoff claim;
- unsupported playoff round: playoff meeting retained without a fabricated round;
- no prior meeting: “No prior meeting found in recorded franchise history.”;
- numeric/string team IDs: normalized through the canonical team-ID helper;
- relocated/renamed teams: canonical IDs remain the history join, while current abbreviations are used for display.

## Intentionally unsupported concepts

V1 omits rivalry ratings, rivalry progression, rivalry labels for non-division opponents, intensity, grudges, revenge/payback copy, fan sentiment, media narratives, chemistry/morale/crowd effects, home-field boosts, AI strategy changes, generated history, and real-world NFL history.

This change makes no simulation, AI, standings, schedule, persistence, worker behavior, or save-schema changes. It does not change game finalization, playoff generation, season rollover, or any stored state.
